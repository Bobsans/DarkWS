# Спецификация DarkWS.Client

Статус: реализовано в DarkWS 4.0.0.  
Дата: 2026-09-15.  
Основа: протокол DarkWS 4.0.0 и поведение браузерного клиента.  
Приоритет: удобство прикладного кода, предсказуемый жизненный цикл, необязательный DI.

## 1. Назначение и границы

Реализовать .NET-клиент DarkWS для консольных, desktop-приложений и фоновых сервисов. Клиент предоставляет запросы с типизированными ответами, серверные уведомления, авторизацию и восстановление соединения.

Один экземпляр клиента представляет одно логическое соединение и одну серверную сессию. Несколько компонентов приложения могут безопасно использовать его одновременно. Для разных пользователей или серверов создаются отдельные экземпляры.

Первая версия поддерживает `net8.0`, `net9.0`, `net10.0`, как текущий репозиторий. Поддержка .NET Framework, Unity, браузерного WebAssembly, Native AOT и мобильного жизненного цикла не входит в гарантии первой версии. Это не утверждение о технической невозможности: такие сценарии требуют собственной проверки перед объявлением поддержки.

Клиент использует общий протокол с полем `data` в запросах и плоским конвертом рассылки. Системные команды — текстовые `auth:<token>` и `logout` с подтверждениями `auth:success`, `auth:failed`, `logout:success`.

## 2. Пакеты и зависимости

| Пакет | Назначение | Зависимости времени выполнения |
| --- | --- | --- |
| `DarkWS.Client` | Клиент, интерфейс, настройки, события, ошибки | Стандартные библиотеки .NET |
| `DarkWS.Client.DependencyInjection` | Расширение `IServiceCollection` | `DarkWS.Client`, `Microsoft.Extensions.DependencyInjection.Abstractions` |

Основной пакет использует `ClientWebSocket` и `System.Text.Json`. Он не ссылается на серверный `DarkWS`, `Microsoft.AspNetCore.App`, DI или Hosting.

`IDarkWsClient` находится в основном пакете: его можно использовать для собственного DI-контейнера и подмены в тестах. Отдельный пакет абстракций, транспортные плагины и фабрика клиентов в первой версии не нужны.

## 3. Требования к удобству

1. Минимальный сценарий: создать клиент и выполнить запрос. Ручная настройка сериализации, идентификаторов и цикла чтения не требуется.
2. DI и Generic Host не обязательны. Поведение клиента одинаково при ручном создании и через DI.
3. Есть явный `ConnectAsync` для ранней проверки подключения и приложений, которые только слушают уведомления. Первый запрос также может подключить новый клиент автоматически.
4. Достаточно указать тип ответа: payload допускает анонимные объекты и прикладные DTO.
5. Действия без результата имеют перегрузку без типа результата: пользователю не нужны фиктивные `Unit` или `object`.
6. Подписка возвращает `IDisposable`; её освобождение явно прекращает доставку новых уведомлений.
7. Асинхронные обработчики поддерживаются без `async void`.
8. Все ожидаемые операции принимают необязательный `CancellationToken` последним аргументом.
9. Настройки проверяются до сетевой активности. Ошибка указывает конкретное свойство.
10. Документация объясняет, какие события требуют переноса выполнения в UI-поток.

## 4. Использование без DI

```csharp
using DarkWS.Client;

await using var client = new DarkWsClient(
    new Uri("wss://example.com/ws"));

var result = await client.RequestAsync<SumResult>(
    "math:sum",
    new { left = 10, right = 20 },
    cancellationToken);

Console.WriteLine(result.Value);

public sealed record SumResult(int Value);
```

Предполагается, что `math:sum` доступен анонимно. Для защищённых действий сначала выполняется авторизация либо задаётся источник токена.

Подписки и явная авторизация:

```csharp
await using var client = new DarkWsClient(new Uri("wss://example.com/ws"));

using var subscription = client.On<MessageCreated>(
    "message:created",
    message => Console.WriteLine(message.Text));

await client.ConnectAsync(cancellationToken);
await client.AuthenticateAsync(accessToken, cancellationToken);

await client.RequestAsync(
    "message:send",
    new { text = "Hello" },
    cancellationToken);

await client.LogoutAsync(cancellationToken);

public sealed record MessageCreated(string Text);
```

Запрос без типа результата ждёт ответ сервера и проверяет ошибку, но игнорирует успешные `data`. Это не отправка без подтверждения.

## 5. Публичный API

Нормативный эскиз основных сигнатур; тела и XML-документация добавляются при реализации.

```csharp
public interface IDarkWsClient : IDisposable, IAsyncDisposable
{
    DarkWsClientState State { get; }

    event EventHandler<DarkWsStateChangedEventArgs>? StateChanged;
    event EventHandler<DarkWsClientErrorEventArgs>? Error;

    Task ConnectAsync(CancellationToken cancellationToken = default);
    Task CloseAsync(CancellationToken cancellationToken = default);

    Task<TResponse> RequestAsync<TResponse>(
        string action, CancellationToken cancellationToken = default);
    Task<TResponse> RequestAsync<TResponse>(
        string action, object? payload,
        CancellationToken cancellationToken = default);

    Task RequestAsync(
        string action, CancellationToken cancellationToken = default);
    Task RequestAsync(
        string action, object? payload,
        CancellationToken cancellationToken = default);

    Task AuthenticateAsync(
        string token, CancellationToken cancellationToken = default);
    Task LogoutAsync(CancellationToken cancellationToken = default);

    IDisposable On(string action, Action handler);
    IDisposable On<T>(string action, Action<T> handler);
    IDisposable OnAsync<T>(
        string action, Func<T, CancellationToken, Task> handler);
}
```

`DarkWsClient` — основная реализация с конструкторами `DarkWsClient(Uri endpoint)` и `DarkWsClient(DarkWsClientOptions options)`.

Строка `action` обязательна, не может быть пустой или состоять из пробелов. Она не нормализуется и сравнивается с учётом регистра. Не вводить клиентские ограничения на формат, которых нет в серверном протоколе.

Перегрузка без payload не отправляет поле `data`; явно переданный `null` отправляется как `"data": null`. Эта разница сохраняется.

### 5.1. Ответы и сериализация

- Настройки по умолчанию основаны на `JsonSerializerDefaults.Web`: camelCase при записи и нечувствительное к регистру сопоставление свойств при чтении.
- `JsonSerializerOptions` можно настроить до создания клиента; клиент сохраняет собственную копию настроек. Изменение исходных options после создания не меняет поведение работающего клиента.
- `RequestAsync<TResponse>` требует наличия поля `data`. Отсутствие поля завершает только конкретный запрос с `DarkWsProtocolException`, поскольку ответ без данных допустим на уровне протокола. Для действий без данных используется перегрузка без типа результата.
- JSON `null` в присутствующем поле `data` обрабатывается правилами `System.Text.Json`. Nullable-аннотации ссылочных типов не дают гарантии проверки во время выполнения; приложение должно выбирать DTO с подходящим контрактом.
- Для динамических данных доступен `RequestAsync<JsonElement>`. Возвращаемый элемент остаётся пригодным после освобождения внутренних буферов и документов.
- Несовместимое с DTO содержимое завершает конкретный запрос ошибкой десериализации; соединение остаётся пригодным для других запросов.

## 6. Необязательная интеграция с DI

```csharp
using DarkWS.Client;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;

var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddDarkWsClient(options =>
{
    options.Endpoint = new Uri("wss://example.com/ws");
});

builder.Services.AddTransient<Calculator>();

using var host = builder.Build();
await host.StartAsync(cancellationToken);

var calculator = host.Services.GetRequiredService<Calculator>();
var result = await calculator.SumAsync(10, 20, cancellationToken);

await host.StopAsync(cancellationToken);

public sealed class Calculator(IDarkWsClient client)
{
    public Task<SumResult> SumAsync(int left, int right, CancellationToken ct) =>
        client.RequestAsync<SumResult>("math:sum", new { left, right }, ct);
}

public sealed record SumResult(int Value);
```

### 6.1. Регистрация и владение

- `AddDarkWsClient(Action<DarkWsClientOptions>)` регистрирует один singleton `IDarkWsClient`. Внедрение конкретного `DarkWsClient` расширением не обещается.
- Есть перегрузка `AddDarkWsClient(Action<IServiceProvider, DarkWsClientOptions>)` для получения прикладного источника токена или конфигурации. Делегат выполняется один раз при создании экземпляра.
- Регистрация и получение сервиса не открывают соединение. Его открывает первый запрос, авторизация или явный `ConnectAsync`.
- Контейнер создаёт и освобождает экземпляр. Потребители, получившие его через конструктор, не вызывают `Dispose`/`DisposeAsync` клиента; своими подписками они владеют самостоятельно.
- Основной клиент поддерживает также синхронный `Dispose`, чтобы обычное освобождение DI-контейнера не требовало асинхронного API.
- Повторный вызов `AddDarkWsClient` либо конфликт с уже зарегистрированным `IDarkWsClient` выбрасывает понятное исключение до изменения регистраций. Конфигурация не перезаписывается молча.
- Расширение не вызывает `BuildServiceProvider` и не создаёт собственный контейнер.
- `IHostedService` автоматически не добавляется. Для раннего подключения приложение вызывает `ConnectAsync` в своём startup-коде или hosted service.
- Singleton подходит для одной общей серверной учётной записи. Для пользовательских сессий приложение явно регистрирует отдельные scoped-экземпляры через фабрику стандартного DI. Это описывается примером в документации.
- Делегаты singleton-клиента не должны захватывать scoped-сервисы. Если нужна scoped-операция, приложение само создаёт scope на время этой операции.

Named/keyed-регистрации и специальный client factory не входят в первое расширение. Несколько соединений доступны через обычное создание клиентов и стандартные возможности контейнера.

## 7. Подключение и восстановление

Состояния: `Disconnected`, `Connecting`, `Connected`, `Reconnecting`, `Disposed`.

`Connected` означает готовность принимать прикладные запросы: WebSocket открыт, настроенная автоматическая авторизация завершена успешно.

| Ситуация | Поведение |
| --- | --- |
| Новый клиент | `Disconnected`; нет сетевой активности и таймеров |
| Первый запрос или `ConnectAsync` | Запуск подключения |
| Несколько одновременных вызовов | Одна общая попытка подключения |
| Отмена одного ожидающего вызова | Отменяется только его ожидание |
| Успешное подключение | `Connected`, запуск heartbeat |
| Неожиданное закрытие | Все отправленные ожидающие запросы получают ошибку; при включённом reconnect начинается восстановление |
| Запрос во время reconnect | Ждёт готовности в пределах `ConnectionTimeout`, затем отправляется один раз |
| `CloseAsync` | Остановка reconnect, закрытие сокета, завершение ожидающих запросов и ожиданий подключения ошибкой |
| Запрос после явного закрытия | Ошибка закрытого соединения; самопроизвольного открытия нет |
| `ConnectAsync` после явного закрытия | Разрешает новый цикл подключения |
| `Dispose`/`DisposeAsync` | Терминальное освобождение; дальнейшие операции бросают `ObjectDisposedException` |

При выключенном reconnect новый цикл после обрыва запускается явным `ConnectAsync`. Первоначальная неуспешная попытка также может повторяться при включённом reconnect, пока существует активный цикл подключения; истечение ожидания отдельного вызова не останавливает общий цикл. Остановить его можно через `CloseAsync` или освобождение клиента.

Повторы подключения используют экспоненциальную задержку с jitter: базовая задержка 1 секунда, верхний предел 30 секунд. После готового подключения задержка сбрасывается. На экземпляр существует не более одной попытки и одного таймера reconnect.

Ошибки конфигурации, отказ авторизации и HTTP 401/403 при upgrade не запускают бесконечные повторы. Они завершают цикл с ошибкой до явного `ConnectAsync` после исправления причины. Для других ошибок транспорта reconnect действует согласно настройке.

Сокет каждой попытки имеет собственный жизненный цикл. Позднее завершение старой попытки не может изменить состояние нового соединения или завершить его запросы.

`CloseAsync` имеет ограниченное ожидание close handshake; после таймаута сокет прерывается. Отмена ожидания закрытия не оставляет reconnect активным. Повторное закрытие и освобождение безопасны.

`DisposeAsync` освобождает транспорт и ожидает завершения внутренних сетевых задач. `Dispose` немедленно отменяет внутреннюю работу и прерывает сокет без блокирующего ожидания пользовательских обработчиков. Асинхронное освобождение также не может бесконечно ждать обработчик, который игнорирует отмену.

## 8. Запросы, отмена и ошибки

Каждый запрос получает уникальный строковый `id`, отличный от `@` и `@auth`. Ответы сопоставляются по `id`, независимо от порядка прихода. Ожидание ответа регистрируется до начала отправки, чтобы не потерять быстрый ответ; ошибка записи удаляет регистрацию.

Стадии ожидания:

1. Готовность соединения — `ConnectionTimeout`.
2. Ожидание очереди отправки и сама отправка — `SendTimeout`.
3. Ответ после успешной отправки — `RequestTimeout`.

Суммарное время может достигать суммы трёх таймаутов. `CancellationToken` позволяет ограничить всю операцию более коротким сроком. Отдельный параметр таймаута в каждой перегрузке не вводится.

- Отмена до отправки исключает отправку, если она ещё не началась.
- Отмена после начала отправки прекращает ожидание вызывающего кода, но не передаётся как отмена общего WebSocket. Она не гарантирует, что сервер не получил или не выполнил команду.
- Превышение транспортного `SendTimeout` после начала записи прерывает повреждённое/неопределённое соединение и завершает его остальные запросы ошибкой. Истечение ожидания очереди до записи не требует закрытия исправного сокета.
- Таймаут ответа не отменяет выполнение на сервере: отдельного протокола отмены нет.
- Ответ после отмены/таймаута и повторный ответ на завершённый `id` игнорируются.
- Любое завершение удаляет запрос из таблицы ожиданий и освобождает связанные регистрации и таймеры.
- Автоматической повторной отправки уже начатых запросов нет, в том числе после reconnect. Повтор бизнес-команды — решение приложения.
- `MaxPendingRequests` учитывает и запросы, ожидающие подключения/отправки. Превышение завершается немедленной локальной ошибкой, не создавая неограниченную очередь.

Публичные ошибки:

| Ошибка | Контракт |
| --- | --- |
| `DarkWsResponseException` | Серверный `Code`, опциональный `ErrorData` типа `JsonElement?`, `RequestId`, `Action`; унаследованное `Exception.Data` не переопределяется |
| `DarkWsConnectionException` | Ошибка соединения, доступные close status/reason и исходная причина |
| `DarkWsTimeoutException : TimeoutException` | Стадия `Connection`, `Send` или `Response` |
| `DarkWsProtocolException` | Некорректный wire-формат, неподдерживаемый тип сообщения или превышение его размера |
| `DarkWsClientLimitException` | Превышение лимита запросов или очереди уведомлений |
| `JsonException` | Ошибка сериализации payload или преобразования `data` в DTO |
| `OperationCanceledException` | Отмена конкретного вызова его токеном |
| `ObjectDisposedException` | Обращение к освобождённому клиенту |

Ошибка ответа определяется наличием поля `error`, даже если код — пустая строка. При наличии и `data`, и `error` ответ считается ошибкой. Значение `error` другого типа, кроме строки, — нарушение протокола.

## 9. Авторизация

Поддерживаются два независимых уровня:

1. HTTP upgrade: callback настройки `ClientWebSocketOptions` перед каждой попыткой, например для заголовка `Authorization` или cookie.
2. Сессия DarkWS: `AuthenticateAsync(token)` и `LogoutAsync()`, использующие текстовые команды без `id` и ожидающие текстового подтверждения.

Callback настройки соединения асинхронный, вызывается перед каждой попыткой и позволяет получить актуальные credentials. Он не получает доступ к самому сокету.

Для автоматического восстановления сессии есть необязательный `AuthenticationTokenProvider`. Он вызывается после открытия каждого нового сокета; полученный непустой токен отправляется через `auth:<token>` до перехода в `Connected`. Обычные запросы ждут результата. Внутренняя команда авторизации не ждёт той же готовности, чтобы не создавать взаимную блокировку.

Если provider задан, `null` или пустой токен считается отсутствием требуемых credentials и завершает подключение ошибкой. Анонимное подключение используется, когда provider не задан.

Ручной `AuthenticateAsync` не сохраняет переданный токен для reconnect. Без provider переподключение восстанавливает только транспорт и авторизацию, выполненную сервером на HTTP upgrade.

`LogoutAsync` запрещает автоматическую авторизацию через provider уже при начале операции, чтобы обрыв во время logout не восстановил прежнюю сессию. Успех возвращается только после подтверждения сервера. Для возобновления автоматической авторизации приложение обновляет свой источник токена и успешно вызывает `AuthenticateAsync`; после этого provider снова используется для будущих подключений.

Эта блокировка не меняет заголовки/cookie HTTP upgrade: их источник принадлежит приложению и должен быть очищен им при logout. Это явно объясняется в примере авторизации.

Ручные операции authenticate/logout выполняются последовательно. Вызовы авторизации во время восстановления ждут завершения текущей попытки; для исправления отказавшего provider сначала обновляется его источник и вызывается `ConnectAsync`.

`auth:failed` вызывает `DarkWsResponseException` с `Code = "auth:failed"`, `Action = "auth"` и пустым `RequestId`. При таймауте или отмене отправленной системной команды сокет закрывается: подтверждение без `id` нельзя безопасно сопоставить со следующей командой. Значение токена в диагностику не включается.

Авторизация не обещает отката уже запущенных действий. Приложение, которому важен порядок «войти, затем выполнить защищённую команду», должно дождаться `AuthenticateAsync` перед отправкой команды.

Refresh-протокол, хранение паролей, OAuth-клиент и расписание обновления токенов не входят в пакет.

## 10. Подписки и события

- `On<T>(action, handler)` сопоставляет `action` из `data.action` broadcast-сообщения; обработчик получает десериализованное `data.data`.
- `On(action, handler)` поддерживает уведомления без payload и игнорирует payload, если он присутствует.
- Несколько подписчиков на одно действие допустимы. Подписки сохраняются при reconnect.
- Отписка идемпотентна. После её возврата новые вызовы обработчика не начинаются; уже выполняющийся обработчик может завершиться.
- Уведомление без подписчиков игнорируется. Ошибка преобразования DTO одного подписчика сообщается через `Error` и не мешает другим подписчикам.
- Пользовательские обработчики не выполняются внутри цикла чтения сокета. Медленный обработчик не задерживает ответы на запросы и pong.
- Уведомления обрабатываются последовательно в порядке получения, подписчики — в порядке регистрации. `OnAsync` ожидается диспетчером уведомлений; обработчик может выполнить и дождаться обычного запроса через тот же клиент.
- Очередь уведомлений ограничена `NotificationQueueCapacity`. При переполнении клиент сообщает ошибку и останавливает цикл подключения до явного `ConnectAsync`; молчаливого выбрасывания уведомлений нет.
- При потере соединения ещё не начатые уведомления старого соединения удаляются, токен выполняющегося async-обработчика отменяется. Документация требует обновлять прикладное состояние после reconnect.
- Протокол не гарантирует доставку рассылок во время отсутствия соединения и не воспроизводит историю событий.
- `StateChanged` сообщает предыдущее и новое состояние, а также доступную причину перехода. `Error` предназначен для фоновых ошибок и ошибок обработчиков; серверные ошибки конкретных запросов возвращаются через их `Task`.
- Обработчики событий не вызываются под внутренней блокировкой или в сетевом цикле. Их исключения не разрывают соединение; исключение из самого обработчика `Error` не вызывает рекурсивный `Error`.
- События и подписки не захватывают `SynchronizationContext`. Перенос в UI-поток выполняется приложением; документация содержит короткий пример.

## 11. Настройки и значения по умолчанию

| Свойство | По умолчанию | Назначение |
| --- | --- | --- |
| `Endpoint` | Обязательно | Абсолютный URI с `ws`/`wss`, без fragment и userinfo |
| `ConnectionTimeout` | 30 секунд | Ожидание готовности и предел отдельной попытки, включая callback/provider/auth |
| `SendTimeout` | 30 секунд | Очередь отправки и транспортная запись |
| `RequestTimeout` | 5 минут | Ожидание ответа после отправки |
| `CloseTimeout` | 5 секунд | Ожидание закрытия сокета |
| `Reconnect` | `true` | Восстановление после транспортного обрыва |
| `PingInterval` | 30 секунд | Прикладной текстовый `ping` |
| `PongTimeout` | 30 секунд | Ожидание соответствующего следующего `pong` |
| `MaxMessageSizeBytes` | 1 MiB | Лимит собранного входящего сообщения |
| `MaxPendingRequests` | 256 | Лимит прикладных запросов, включая ожидающие соединения |
| `NotificationQueueCapacity` | 256 | Число ожидающих уведомлений |
| `JsonOptions` | Web defaults | Настройки JSON |
| `ConfigureWebSocketOptionsAsync` | `null` | `Func<ClientWebSocketOptions, CancellationToken, ValueTask>` перед каждой попыткой |
| `AuthenticationTokenProvider` | `null` | `Func<CancellationToken, ValueTask<string?>>` для автоматической сессии |

Таймауты должны быть положительными и поддерживаться используемыми .NET-таймерами. Только `RequestTimeout` допускает `Timeout.InfiniteTimeSpan`; ноль не означает отключение. Лимиты должны быть положительными.

Ping отправляется только на открытом сокете через общий механизм сериализации записей. Следующий ping не отправляется, пока не завершено ожидание предыдущего pong. Отсчёт `PongTimeout` начинается после успешной записи ping. Обычный ответ на запрос не заменяет pong. Превышение срока считается транспортным обрывом.

Собственные прикладные ping/pong работают на всех целевых .NET и не зависят от наличия транспортного `KeepAliveTimeout`. Серверная перегрузка может задерживать pong; значения таймаутов должны быть настраиваемыми.

## 12. Протокол, ограничения и безопасность

| Направление | Формат |
| --- | --- |
| Запрос | `{ "id": "...", "action": "...", "data": ... }` |
| Успех | `{ "id": "...", "data": ... }`, `data` может отсутствовать |
| Ошибка | `{ "id": "...", "error": "...", "data": ... }` |
| Рассылка | `{ "id": "@", "action": "...", "data": ... }` |
| Авторизация | Текст `auth:<token>` → `auth:success` или `auth:failed` |
| Выход | Текст `logout` → `logout:success` |
| Heartbeat | Текстовые `ping` и `pong` |

- Использовать один цикл чтения и последовательные записи: `ClientWebSocket` не поддерживает несколько одновременных send или receive.
- Собирать фрагменты до конца сообщения; лимит применять к сумме байтов до дальнейшего выделения памяти. Учитывать границы UTF-8 между фрагментами.
- Превышение входящего лимита закрывает соединение со статусом 1009; неподдерживаемое бинарное сообщение — 1003. Некорректный UTF-8 — 1007. Невалидный JSON/envelope — ошибка протокола с закрытием 1002. Такие ошибки останавливают автоматическое восстановление до явного `ConnectAsync`.
- Неизвестный корректный response id и legacy `@auth` игнорируются. Отсутствующий/нестроковый id — ошибка протокола.
- Ошибка DTO внутри корректного envelope не равна ошибке wire-протокола и обрабатывается по разделам запросов и подписок.
- Клиент не изменяет глобальные настройки TLS и не отключает проверку сертификата по умолчанию.
- Токены, payload и полный URI с query не включаются в сообщения диагностических событий или исключений по умолчанию. Данные контролируемой серверной ошибки доступны явно через `ErrorData` и остаются валидными после освобождения внутренних JSON-документов.
- Ограничения запросов и очереди применяются также при недоступном сервере. Неограниченный запуск задач на каждое уведомление запрещён.
- Внутренние операции auth и heartbeat должны иметь возможность выполняться при достигнутом лимите прикладных запросов; это ограниченное служебное исключение, а не дополнительная неограниченная очередь.

## 13. Проверки и критерии приёмки

Использовать существующие инструменты тестирования репозитория. Для управляемых обрывов/таймаутов допустим локальный тестовый WebSocket-сервер; совместимость обязательно проверяется также с реальным DarkWS-сервером.

| Область | Обязательное подтверждение |
| --- | --- |
| Удобство | Примеры без DI и с DI собираются и выполняют запрос к тестовому серверу |
| Контракт | Payload отсутствует/null/DTO, результат отсутствует/null/DTO, серверная ошибка с данными, broadcast |
| Конкурентность | Параллельные запросы получают свои ответы при обратном порядке ответов; нет конкурентных записей |
| Отмена | Отмена одного запроса и одного ожидания connect не ломает соседние операции |
| Таймауты | Проверены три стадии, отсутствие утечек pending-запросов, игнорирование поздних ответов |
| Восстановление | Один reconnect-цикл; pending завершаются ошибкой; отправленные команды не повторяются; старый сокет не влияет на новый |
| Авторизация | Успех/отказ authenticate, подтверждённый logout, provider на reconnect, остановка после 401/403, logout запрещает повторный вызов provider до нового входа |
| Подписки | Несколько слушателей, отписка, async-обработчик с вложенным запросом, ошибка одного слушателя, порядок и переполнение |
| Heartbeat | Ping/pong, отсутствие pong, остановка таймеров при закрытии, восстановление после таймаута |
| Входящие данные | Фрагментация и UTF-8, предел размера, binary, malformed JSON/envelope, неизвестный id |
| Жизненный цикл | Повторные connect/close/dispose, dispose во время отправки/подключения/обработчика, отсутствие новых callbacks после отписки |
| DI | Один экземпляр для разных потребителей; создание не подключает; контейнер освобождает клиент; конфликт регистрации предсказуем; ручной scoped-сценарий изолирует две сессии |
| Упаковка | Основной NuGet не требует ASP.NET/DI; DI-пакет зависит от основного; XML/PDB присутствуют; примеры работают из собранных пакетов на всех TFM |

Проверить ошибки гонок повторяемыми сценариями, а не только одиночным happy path. Не использовать произвольные большие задержки для синхронизации тестов.

Новые пакеты включаются в существующие проверки покрытия, public API baseline, package-consumer tests и синхронизацию версий. Текущие пороги покрытия репозитория сохраняются.

## 15. Что отложено

- Генерация RPC-прокси, атрибуты на клиентских сервисах и сканирование сборок.
- Durable/offline-очередь, гарантированная доставка, автоматические повторы бизнес-команд.
- Потоки данных и файловые загрузки поверх отдельного бинарного протокола.
- Универсальные retry/middleware pipelines и поддержка альтернативных транспортов.
- Автоматическое восстановление пропущенных broadcast-событий.
- Отдельные адаптеры UI-фреймворков, собственный DI-контейнер и управление OAuth.

Эти возможности добавляются при конкретном пользовательском сценарии. Первая версия остаётся обычным .NET-клиентом с понятными методами, опциональным DI и проверенным жизненным циклом.
